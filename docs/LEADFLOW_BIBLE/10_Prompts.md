# LeadFlow Prompts

## Objetivo

Padronizar como diferentes papéis operam dentro do LeadFlow, garantindo que qualquer execução — humana ou por IA — siga a mesma Visão, Arquitetura e Padrões do produto.

---

## Filosofia

Um prompt define um papel, não uma pessoa.

O papel deve se comportar da mesma forma independentemente de quem o executa, porque ele segue as regras do produto, não preferências individuais.

Nenhum prompt substitui a Bible. Todo prompt deve ser consistente com ela.

---

## Estrutura de um Prompt

- **Papel** — quem o prompt representa
- **Objetivo** — o que esse papel deve alcançar
- **Contexto** — o que esse papel precisa saber antes de agir
- **Regras** — limites e restrições do papel
- **Formato de saída** — como o resultado deve ser entregue

---

## Papéis Definidos

- **Backend Engineer** — implementa e mantém regras de negócio, API e dados
- **Frontend Engineer** — implementa interface e experiência do usuário
- **UX** — organiza fluxo, clareza e usabilidade do produto
- **Vendas** — traduz inteligência comercial em abordagem e discurso
- **Copiloto** — orienta o usuário final durante o uso do produto

---

## Regras para Criar um Novo Prompt

- Todo prompt deve referenciar a Visão e a Arquitetura do produto
- Nenhum prompt pode contradizer os Coding Standards
- Prompts devem ser objetivos, curtos e verificáveis
- Um prompt por papel, sem sobreposição de responsabilidade
- Prompts não descrevem tarefas específicas, apenas o papel

---

## Ciclo de Vida de um Prompt

Criação

↓

Validação contra a Bible

↓

Uso

↓

Revisão periódica

↓

Atualização ou Aposentadoria

**Criação** — o papel é definido a partir de uma necessidade real do produto.

**Validação contra a Bible** — o prompt é conferido contra Visão, Arquitetura e Coding Standards.

**Uso** — o prompt orienta execuções reais, humanas ou por IA.

**Revisão periódica** — o prompt é reavaliado junto das demais revisões da documentação.

**Atualização ou Aposentadoria** — o prompt é ajustado para continuar válido ou removido quando o papel deixa de existir.

---

## Critérios de Qualidade

- Define claramente o papel e seus limites
- É consistente com a Visão, a Arquitetura e os Coding Standards
- Não deixa margem para comportamento contraditório
- Pode ser seguido sem contexto adicional além da Bible
- Produz resultado verificável, não apenas plausível

---

## Manutenção

Prompts são revisados sempre que a Visão, a Arquitetura, o Produto ou os Coding Standards mudarem.

Um prompt desatualizado é tratado como um bug de documentação.

---

## Princípios

- Papel antes de pessoa
- Consistência antes de personalização
- Clareza antes de completude
- Todo prompt serve à Bible, nunca a substitui
